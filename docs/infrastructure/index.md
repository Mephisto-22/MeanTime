# Infrastructure Guide

Terraform for MeanTime's AWS environments lives in the `infra/` folder. Dev and Prod live in **separate AWS accounts** (members of one AWS Organization) and are built from the same modules.

- **Dev** is private: no public IP, load balancer or domain. Developers reach it through a Session Manager tunnel.
- **Prod** is public, behind a load balancer.

Each environment can be brought up for testing or a demo and torn down afterwards.

---

## Layout

```text
infra/
├── modules/
│   ├── app/               # ECS cluster, service and task; builds and pushes images; Prod load balancer
│   ├── ecr/               # image repositories for our own images
│   ├── github-oidc/       # lets GitHub Actions sign in to AWS (see "From GitHub")
│   ├── network/           # VPC: private with a NAT gateway (Dev) or public for the load balancer (Prod)
│   └── state-bucket/      # S3 bucket that stores Terraform state (used by bootstrap)
├── bootstrap/
│   ├── dev/               # one-time: creates Dev's state bucket, writes envs/dev/backend.hcl
│   └── prod/              # one-time: creates Prod's state bucket, writes envs/prod/backend.hcl
└── envs/
    ├── dev/
    │   ├── backend.hcl    # generated by bootstrap; shared backend settings for dev/*
    │   ├── base/          # kept between demos: ECR image repositories, GitHub Actions role
    │   └── app/           # temporary: network and ECS service
    └── prod/
        ├── backend.hcl
        ├── base/
        └── app/
```

Each folder under `envs/` is its own Terraform root with its own state file (`base/terraform.tfstate` and `app/terraform.tfstate` in that environment's bucket). That lets you tear down `app` without touching `base`.

## Prerequisites

- **Terraform 1.10 or later.** The S3 backend locks state with `use_lockfile`, which needs 1.10.
- **AWS CLI v2.**
- **Docker, running.** `apply` in an `app` folder builds and pushes the images on your machine.
- **AWS Session Manager plugin,** to open Dev: `winget install Amazon.SessionManagerPlugin` on Windows.
- **An AWS login for each account,** as CLI profiles named `meantime-dev` and `meantime-prod`:

  ```bash
  # Sign in to the Dev account in the AWS console first, then:
  aws login --profile meantime-dev
  aws configure set region us-east-2 --profile meantime-dev

  # Same for Prod:
  aws login --profile meantime-prod
  aws configure set region us-east-2 --profile meantime-prod
  ```

  Check that each profile points at the right account:

  ```bash
  aws sts get-caller-identity --profile meantime-dev
  aws sts get-caller-identity --profile meantime-prod
  ```

  Logins expire. If Terraform reports expired or missing credentials, run `aws login --profile <profile>` again.

No AWS access keys are stored in this repository or on your machine. Terraform uses your temporary login.

## First-time setup

Each account needs an S3 bucket for Terraform state before anything else can be applied. Bootstrap creates it, once per account. It has already been done for MeanTime's accounts, so you only need this when setting up a new account:

```bash
cd infra/bootstrap/dev
terraform init
terraform plan      # review: one S3 bucket and its settings, plus backend.hcl
terraform apply

cd ../prod
terraform init
terraform plan
terraform apply
```

Then commit the generated `envs/dev/backend.hcl` and `envs/prod/backend.hcl`.

Bootstrap keeps its own state in a local `terraform.tfstate` file (not committed), because the bucket doesn't exist until bootstrap creates it. Losing that local file is harmless: the bucket keeps working. The bucket is protected with `prevent_destroy`, so `terraform destroy` here refuses to delete it.

## Everyday use

Run Terraform from the folder for the environment and layer you want, always passing that environment's `backend.hcl` to `init`:

```bash
cd infra/envs/dev/app
terraform init -backend-config=../backend.hcl   # once per folder, or after changing providers
terraform plan                                   # preview changes
terraform apply                                  # bring it up / apply changes
terraform destroy                                # tear it down
```

- **Bring Dev up for testing:** `apply` in `envs/dev/base` (only the first time), then `envs/dev/app`.
- **Tear Dev down afterwards:** `destroy` in `envs/dev/app`. Leave `base` alone.
- **Prod** works the same way, from `envs/prod/`.

`apply` in an `app` folder builds both images from your working copy, pushes them to ECR, and waits until the app is running and healthy. Expect about 5 minutes. The database starts empty every time, so register a new account after each `apply`.

While an environment is up it costs a few cents an hour (Dev: task and NAT gateway; Prod: task and load balancer). `destroy` stops all of it.

## From GitHub

You can also bring an environment up or down from GitHub, without Terraform, Docker or an AWS login on your machine:

1. Open the repository's **Actions** tab and choose **Environment**.
2. Select **Run workflow**, pick the branch, the environment (`dev` or `prod`) and the action (`up` or `down`), then **Run workflow**.
3. When the run finishes, its summary page shows the Prod URL, or the commands to open the Dev tunnel.

`up` runs `terraform apply` in `envs/<environment>/app` and `down` runs `terraform destroy` there, exactly as on your machine. The images are built from the branch you picked. Runs share the same Terraform state as local runs, so it doesn't matter where an environment was brought up; it can be torn down from either place.

- **The Run workflow button only appears once `environment.yml` is on `main`.** GitHub only offers manual runs for workflows on the default branch.
- **Prod can only be changed from `main`; Dev from `dev` or `main`.** AWS only trusts GitHub runs from those branches (`infra/modules/github-oidc`), so a run from any other branch fails at **Sign in to AWS**.
- Only one run per environment goes at a time. A second run waits for the first to finish.
- Opening the Dev tunnel still needs the Session Manager plugin and an AWS login on your machine (see [Open Dev](#open-dev)).

**One-time setup** (a repository admin): GitHub needs to know which AWS role to use in each account. Get each role's ARN:

```bash
cd infra/envs/dev/base
terraform output -raw github_actions_role_arn

cd ../../prod/base
terraform output -raw github_actions_role_arn
```

Then, in the repository's **Settings → Secrets and variables → Actions → Variables**, add them as `AWS_DEV_ROLE_ARN` and `AWS_PROD_ROLE_ARN`. They're variables rather than secrets because a role ARN isn't a credential: only GitHub runs from the trusted branches can use it.

## Open Dev

Dev has no public address. Open it through a Session Manager tunnel to `http://localhost:3000`:

```powershell
cd infra/envs/dev/app
terraform output -raw dev_tunnel_command_powershell   # PowerShell
terraform output -raw dev_tunnel_command              # Git Bash, macOS, Linux
```

Paste the printed command into the same kind of shell and leave it running, then open http://localhost:3000. Press Ctrl+C to close the tunnel. Stop the local dev stack first (`docker compose stop frontend`), since it also uses port 3000.

---

## Open Prod

```bash
cd infra/envs/prod/app
terraform output app_url
```

The URL changes every time Prod is rebuilt, so check it after each `apply`. It's plain HTTP for now, so browsers mark it "Not secure".

## Images

The `base` layer creates two ECR repositories in each account, `meantime/frontend` and `meantime/backend`, and keeps the 10 most recent images in each.

`apply` in an `app` folder builds the images from `backend/docker/Dockerfile.prod` and `frontend/docker/Dockerfile.prod`. Each one is tagged with a fingerprint of its source, so it's only rebuilt and pushed when its code changes. Pushes use a private Docker config in `.terraform/docker-ecr/` instead of `docker login`, which fails on Windows. Because ECR hands out a new login token each time, every `plan` shows `local_sensitive_file.docker_config` as changed. That's expected.

`destroy` leaves pushed images in ECR, because the repositories belong to `base`.

Third-party images, such as `postgres:18-alpine`, are pulled straight from Docker Hub. Dev's task has no public IP, but it reaches the internet through a NAT gateway.

## Troubleshooting

- **"Your session has expired" / "No valid credential sources found":** run `aws login --profile meantime-dev` (or `meantime-prod`) again.
- **`terraform` not recognized right after installing it:** restart VS Code (or open a new terminal outside it) so it picks up the new `PATH`.
- **`terraform init` fails with "connection forcibly closed":** a flaky download from HashiCorp's servers. Run it again.
- **The tunnel says port 3000 is in use:** stop the local dev stack's frontend, or whatever else is on port 3000.
- **Logs:** each container's logs are in CloudWatch under `terraform output log_group`.
