# Infrastructure Guide

Terraform for MeanTime's AWS environments lives in the `infra/` folder. Dev and Prod live in **separate AWS accounts** (members of one AWS Organization) and are built from the same modules.

- **Dev** is private: no public IP, load balancer or domain. Developers reach it through a Session Manager tunnel.
- **Prod** is public, behind a load balancer, at https://meantime.click.

Each environment can be brought up for testing or a demo and torn down afterwards.

---

## Layout

```text
infra/
├── modules/
│   ├── app/               # ECS cluster, service and task; builds and pushes images; Prod load balancer and HTTPS
│   ├── ecr/               # image repositories for our own images
│   ├── github-oidc/       # lets GitHub Actions sign in to AWS (see "From GitHub")
│   ├── network/           # VPC: private with a NAT gateway (Dev) or public for the load balancer (Prod)
│   ├── persistent-data/   # the database's files (EFS), secrets and Google sign-in entries, kept when the app is torn down
│   └── state-bucket/      # S3 bucket that stores Terraform state (used by bootstrap)
├── bootstrap/
│   ├── dev/               # one-time: creates Dev's state bucket, writes envs/dev/backend.hcl
│   └── prod/              # one-time: creates Prod's state bucket, writes envs/prod/backend.hcl
└── envs/
    ├── dev/
    │   ├── backend.hcl    # generated by bootstrap; shared backend settings for dev/*
    │   ├── base/          # kept between demos: ECR image repositories, GitHub Actions role, database data
    │   └── app/           # temporary: network and ECS service
    └── prod/
        ├── backend.hcl
        ├── base/          # as in Dev, plus the domain's DNS zone and HTTPS certificate (domain.tf)
        └── app/
```

Each folder under `envs/` is its own Terraform root with its own state file (`base/terraform.tfstate` and `app/terraform.tfstate` in that environment's bucket). That lets you tear down `app` without touching `base`.

## Prerequisites

- **Terraform 1.10 or later.** The S3 backend locks state with `use_lockfile`, which needs 1.10.
- **AWS CLI v2.**
- **Docker, running.** `apply` in an `app` folder builds and pushes the images on your machine.
- **AWS Session Manager plugin,** to open Dev: `winget install Amazon.SessionManagerPlugin` on Windows.
- **An AWS login for each account,** as CLI profiles named `meantime-dev` and `meantime-prod`:

  ```bash
  # Sign in to the Dev account in the AWS console first, then:
  aws login --profile meantime-dev
  aws configure set region us-east-2 --profile meantime-dev

  # Same for Prod:
  aws login --profile meantime-prod
  aws configure set region us-east-2 --profile meantime-prod
  ```

  Check that each profile points at the right account:

  ```bash
  aws sts get-caller-identity --profile meantime-dev
  aws sts get-caller-identity --profile meantime-prod
  ```

  Logins expire. If Terraform reports expired or missing credentials, run `aws login --profile <profile>` again.

No AWS access keys are stored in this repository or on your machine. Terraform uses your temporary login.

## First-time setup

Each account needs an S3 bucket for Terraform state before anything else can be applied. Bootstrap creates it, once per account. It has already been done for MeanTime's accounts, so you only need this when setting up a new account:

```bash
cd infra/bootstrap/dev
terraform init
terraform plan      # review: one S3 bucket and its settings, plus backend.hcl
terraform apply

cd ../prod
terraform init
terraform plan
terraform apply
```

Then commit the generated `envs/dev/backend.hcl` and `envs/prod/backend.hcl`.

Bootstrap keeps its own state in a local `terraform.tfstate` file (not committed), because the bucket doesn't exist until bootstrap creates it. Losing that local file is harmless: the bucket keeps working. The bucket is protected with `prevent_destroy`, so `terraform destroy` here refuses to delete it.

## Everyday use

Run Terraform from the folder for the environment and layer you want, always passing that environment's `backend.hcl` to `init`:

```bash
cd infra/envs/dev/app
terraform init -backend-config=../backend.hcl   # once per folder, or after changing providers
terraform plan                                   # preview changes
terraform apply                                  # bring it up / apply changes
terraform destroy                                # tear it down
```

- **Bring Dev up for testing:** `apply` in `envs/dev/base` (only the first time), then `envs/dev/app`.
- **Tear Dev down afterwards:** `destroy` in `envs/dev/app`. Leave `base` alone.
- **Prod** works the same way, from `envs/prod/`.

`apply` in an `app` folder builds any image that isn't in ECR yet (see [Images](#images)), and waits until the app is running and healthy. Expect about 5 minutes. The database keeps its data between `destroy` and `apply` (see [Database](#database)).

While an environment is up it costs a few cents an hour (Dev: task and NAT gateway; Prod: task and load balancer). `destroy` stops all of it, and a nightly run tears down anything left up (see [From GitHub](#from-github)). Prod's DNS zone costs $0.50 a month whether the app is up or not (see [Domain and HTTPS](#domain-and-https)).

The `app` layer reads entries the `base` layer creates, so apply `base` first whenever it has changed. Otherwise the `app` apply fails because it can't find them.

## From GitHub

You can also bring an environment up or down from GitHub, without Terraform, Docker or an AWS login on your machine:

1. Open the repository's **Actions** tab and choose **Environment**.
2. Select **Run workflow**, pick the branch, the environment (`dev` or `prod`) and the action (`up` or `down`), then **Run workflow**.
3. When the run finishes, its summary page shows the Prod URL, or the commands to open the Dev tunnel.

`up` runs `terraform apply` in `envs/<environment>/app` and `down` runs `terraform destroy` there, exactly as on your machine. The images come from the branch you picked. Runs share the same Terraform state as local runs, so it doesn't matter where an environment was brought up; it can be torn down from either place.

The same workflow also runs on its own:

- **Every night at 1 a.m. Central** (07:00 UTC) it tears down Dev and Prod, so a forgotten environment costs at most one night. The database's data is kept. An environment that's already down is left as it is.
- **On every push to `dev` or `main`** that changes `backend/` or `frontend/`, it builds the images and pushes them to ECR: Dev's on `dev`, Prod's on `main`. The environment stays as it was; the next `up` uses those images instead of building them.

- **The Run workflow button only appears once `environment.yml` is on `main`.** GitHub only offers manual runs for workflows on the default branch.
- **Prod can only be changed from `main`; Dev from `dev` or `main`.** AWS only trusts GitHub runs from those branches (`infra/modules/github-oidc`), so a run from any other branch fails at **Sign in to AWS**.
- Only one run per environment goes at a time. A second run waits for the first to finish.
- The nightly run is a GitHub schedule, which runs from `main` only. GitHub turns schedules off in a repository with no activity for 60 days.
- Opening the Dev tunnel still needs the Session Manager plugin and an AWS login on your machine (see [Open Dev](#open-dev)).

**One-time setup** (a repository admin): GitHub needs to know which AWS role to use in each account. Get each role's ARN:

```bash
cd infra/envs/dev/base
terraform output -raw github_actions_role_arn

cd ../../prod/base
terraform output -raw github_actions_role_arn
```

Then, in the repository's **Settings → Secrets and variables → Actions → Variables**, add them as `AWS_DEV_ROLE_ARN` and `AWS_PROD_ROLE_ARN`. They're variables rather than secrets because a role ARN isn't a credential: only GitHub runs from the trusted branches can use it.

## Open Dev

Dev has no public address. Open it through a Session Manager tunnel to `http://localhost:3000`:

```powershell
cd infra/envs/dev/app
terraform output -raw dev_tunnel_command_powershell   # PowerShell
terraform output -raw dev_tunnel_command              # Git Bash, macOS, Linux
```

Paste the printed command into the same kind of shell and leave it running, then open http://localhost:3000. Press Ctrl+C to close the tunnel. Stop the local dev stack first (`docker compose stop frontend`), since it also uses port 3000.

## Open Prod

Prod is at **https://meantime.click** once the app layer is up. `http://` addresses redirect to HTTPS. `terraform output app_url` in `envs/prod/app` prints the same URL.

## Domain and HTTPS

`meantime.click` is registered at Porkbun, which only handles the registration. Porkbun's nameservers for the domain point to a Route 53 hosted zone, so AWS answers for it:

| Layer | What | Where |
|---|---|---|
| Prod `base` | The hosted zone, and a free ACM certificate for the domain, validated through a DNS record in the zone. ACM renews it on its own. | `envs/prod/base/domain.tf` |
| Prod `app` | An HTTPS listener on the load balancer with that certificate, HTTP redirected to HTTPS, and the domain's record pointing at the load balancer | `modules/app/load_balancer.tf`, turned on by `domain_name` in `envs/prod/app/main.tf` |

The zone and certificate are in `base`, so bringing the app layer up doesn't change the nameservers or wait for a new certificate. Dev has no domain.

If the zone is ever recreated, it gets new nameservers. Print them with `terraform output name_servers` in `envs/prod/base` and enter them at Porkbun under **Authoritative Nameservers**.

**Removing the domain.** The domain is only needed for about a month. To stop using it:

1. In `envs/prod/app/main.tf`, delete the `domain_name` line. On the next `apply`, Prod goes back to plain HTTP at the load balancer's own address (`terraform output app_url`). Remove `https://meantime.click/...` from the Google OAuth client's redirect URIs, and add the new address's URI if Google sign-in should keep working (see the [Google sign-in guide](../google-sign-in.md)). Google only accepts `http://` redirect URIs for `localhost`, so Google sign-in won't work on Prod over plain HTTP.
2. With the app layer down or already applied without the domain, delete the certificate and zone resources from `envs/prod/base/domain.tf` and `apply` in `envs/prod/base`. This stops the $0.50 a month.
3. Make sure auto-renew is off for the domain at Porkbun.

## Images

The `base` layer creates two ECR repositories in each account, `meantime/frontend` and `meantime/backend`, and keeps the 10 most recent images in each.

`apply` in an `app` folder builds the images from `backend/docker/Dockerfile.prod` and `frontend/docker/Dockerfile.prod`. Each one is tagged with a fingerprint of its source. If ECR already has that tag, because the code hasn't changed or the push workflow already built it, the build is skipped. Pushes use a private Docker config in `.terraform/docker-ecr/` instead of `docker login`, which fails on Windows. Because ECR hands out a new login token each time, every `plan` shows `local_sensitive_file.docker_config` as changed. That's expected.

`destroy` leaves pushed images in ECR, because the repositories belong to `base`.

## Database

Postgres runs as a container in the app's task, but its files live on an EFS file system in the `base` layer (`modules/persistent-data`), together with the database password and Django's secret key. So the data survives `destroy` and the nightly teardown, and is back after the next `apply`. Each `apply` connects the file system to the new network; that adds a minute or two to `apply` and `destroy`.

To start over with an empty database, run this with the app layer down:

```bash
cd infra/envs/dev/base
terraform apply -replace=module.persistent_data.aws_efs_file_system.db
```

Destroying the `base` layer deletes the data for good.

The `base` layer also creates two Parameter Store entries for Google sign-in, `/meantime/<env>/google-oauth-client-id` and `/meantime/<env>/google-oauth-client-secret`. Unlike the generated password and key, their values are pasted in by hand in the AWS console, once per account. See the [Google sign-in guide](../google-sign-in.md#in-aws).

Third-party images, such as `postgres:18-alpine`, are pulled straight from Docker Hub. Dev's task has no public IP, but it reaches the internet through a NAT gateway.

## Troubleshooting

- **"Your session has expired" / "No valid credential sources found":** run `aws login --profile meantime-dev` (or `meantime-prod`) again.
- **`terraform` not recognized right after installing it:** restart VS Code (or open a new terminal outside it) so it picks up the new `PATH`.
- **`terraform init` fails with "connection forcibly closed":** a flaky download from HashiCorp's servers. Run it again.
- **The tunnel says port 3000 is in use:** stop the local dev stack's frontend, or whatever else is on port 3000.
- **`app` apply fails with "couldn't find resource" for an SSM parameter:** that environment's `base` layer hasn't been applied since the entry was added. Apply `base` first.
- **The Google sign-in button is missing, or Google says "invalid_client":** the Google entries in Parameter Store still hold the placeholder or were pasted incompletely. Fix them, then bring the app layer up again.
- **Logs:** each container's logs are in CloudWatch under `terraform output log_group`.
